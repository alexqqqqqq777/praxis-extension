# Розгортання вітрини

Дві однакові вітрини, одна адреса. Розширення знає тільки
`https://praxis.51-83-129-254.sslip.io` і про запасну не здогадується.

```
браузер юриста
      │  HTTPS
      ▼
   nginx на VPS          ← TLS, жодних журналів, IP далі не передається
      │
      ├─ 100.70.93.113:8788        основна: adv (Windows), через tailnet
      └─ 100.118.205.24:8788       запасна: Mac Studio, через tailnet
```

Вітрини на самому VPS більше немає: машина слабка, і тримати там урізаний
корпус не було сенсу. VPS лишився тим, чим має бути, — шлюзом TLS, щоб домашня
адреса ніде не світилася.

## Коли вмикається запасна

nginx рахує основну недоступною після двох невдач і тримає цю думку 10 секунд
(`max_fails=2 fail_timeout=10s`). Перехід відбувається і тоді, коли основна
відповіла помилкою, а не лише мовчить — інакше юрист побачив би 502 замість
карток (`proxy_next_upstream error timeout http_502 http_503 http_504`).

Перевірено 17.09.2026: зупинка `adv` — картки далі віддаються зі Studio за
0,67 с, `found` той самий; після підняття основної трафік повертається.

## Чому вузли слухають лише tailnet

Брандмауер на домашній машині вимкнений, тож прив'язка до `0.0.0.0` відкрила б
API всій домашній мережі. Обидва вузли слухають **тільки** свою адресу tailnet
(`--host 100.70.93.113` і `--host 100.118.205.24`): і локальна мережа, і
loopback закриті, перевірено.

Домашня IP-адреса назовні не світиться: браузер бачить лише VPS.

## Приватність на обох шляхах

Після перемикання перевірено: у журналі сервісу 0 записів про запити, у
`access.log` nginx 0 згадок нашого vhost, `tailscaled` трафіку не пише, на
Windows файлів журналу немає. Вивід служби на Windows іде в `nul`.

## Особливості машин

**VPS.** Ubuntu 24.10 знята з підтримки: репозиторії видалені з архіву, `apt`
не працює, оновлень безпеки машина не отримує. Через це Tailscale поставлений
статичним бінарником у `/usr/local`, а не пакетом — системні джерела не
чіпалися. Видаляється зупинкою `tailscaled` і видаленням бінарників.

Маршрути Tailscale навмисно не приймає (`--accept-routes=false`): на VPS уже є
свій WireGuard із мережею `10.5.5.0/24`.

Сусідній сервіс `motion` постійно тримає одне з двох ядер — звідси низький
`CPUWeight` і обмежувач одночасних запитів у вітрині.

**Windows.** Служба через Task Scheduler `PraxisCards`, від SYSTEM, запуск при
завантаженні, авторестарт. Керування:

```powershell
Get-ScheduledTask PraxisCards | Get-ScheduledTaskInfo
Stop-ScheduledTask PraxisCards ; Start-ScheduledTask PraxisCards
```

Перевірка здоровʼя — за адресою tailnet, не `127.0.0.1`:

```powershell
curl.exe -s http://100.70.93.113:8788/health
```

**Mac Studio.** Служба — `~/Library/LaunchAgents/ua.praxis.cards.plist`, копія
з ключем-заглушкою лежить у `deploy/macos/`. Три речі там не косметичні:
`NPA_DB` вказує на той самий зріз (інакше служба знаходить живу базу корпусу і
приєднує її, а її щоночі перебудовують на місці), вузол слухає лише адресу
tailnet, журнали — у `/dev/null`.

Після нічної підміни зрізу службу треба перезапустити:

```bash
launchctl kickstart -k gui/$(id -u)/ua.praxis.cards
```

Це не косметика: процес, що тримає старий файл відкритим, читатиме вчорашні
дані вічно, а 7,5 ГБ старого зрізу не звільняться з диска, доки він живий.
Робить це `praxis-rebuild.sh` корпусу.

## Синтетична перевірка зі шлюза

`praxis-probe.timer` щохвилини питає `/health` у трьох місць: публічної адреси
через nginx (це те, що бачить юрист) і обох вузлів по tailnet. Різниця між
ними й робить сповіщення осмисленим: «лежить adv, працюємо на Studio» замість
«щось не так». Говорить лише про зміну стану, і про падіння — після двох
невдач поспіль.

Пише власні звернення: час, код, мілісекунди. Запитів юриста тут немає.

```bash
sudo install -m 755 tools/probe.py /usr/local/lib/praxis-probe.py
sudo cp deploy/praxis-probe.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now praxis-probe.timer
python3 /usr/local/lib/praxis-probe.py --report --days 1
```

Канал сповіщень — рішення власника: `Environment=PRAXIS_NOTIFY=…` у
`systemctl edit praxis-probe.service`. Поки його немає, зміни стану лишаються
в базі й у journal.

Заміри потрібні ще й для одного відкритого питання: запасна відповідає швидше
за основну чи це здалося. Порівнювати треба p95 за добу, окремо вдень і вночі
(на Studio 02:30–07:00 працюють конвеєри), — `--report` так і друкує.

## nginx-сирота на шлюзі

Станом на 17.09.2026 nginx на VPS працює **повз systemd**: юніт `failed` з
01.09, а сам процес живий із тієї ж хвилини, батько — `init`. Підняв його не
людина і не systemd, а плагін `nginx` у certbot: коли `reload` не вдався, він
стартує nginx самотужки, і через тринадцять секунд юніт упав — порт уже був
зайнятий.

Наслідки, які видно не одразу:

* `systemctl reload nginx` мовчки не робить нічого («Unit cannot be reloaded
  because it is inactive»). Для Praxis це поки не страшно — його `renew_hook`
  шле сигнал за pid-файлом, і сигнал доходить до сироти;
* а от у `cam` і `51-83-129-254.sslip.io` (live-translator) перезавантаження
  після оновлення сертифіката немає **зовсім**: новий файл ляже на диск, nginx
  і далі віддаватиме старий. `cam` оновлюється близько 09.10, старий діє до
  08.11;
* `51-83-129-254.sslip.io` оновлюється способом `standalone`, якому потрібен
  вільний 80-й порт — а його тримає nginx;
* якщо процес-сирота помре, його ніхто не підніме.

Корінь — два мертві сертифікати, `bazhanka.com` і `api.bazhanka.com`: лише їм
потрібен плагін nginx, обидва прострочені, сайтів за ними немає, а certbot
намагається оновити їх двічі на добу. Поки їхні конфігурації лежать на диску,
сирота повертатиметься після будь-якої невдалої перезагрузки.

Повернення під systemd — `deploy/vps-adopt-nginx.sh` (простій близько секунди,
з відкатом і звіркою «до / після»). Видалення мертвих сертифікатів і
переведення live-translator на `webroot` — окремі команди, рішення власника;
вони в коментарі до скрипта.

Проба зі шлюза тепер питає ще й `systemctl is-active nginx`: сирота прожив
сімнадцять днів саме тому, що всі перевірки дивилися «чи відкривається сайт», а
сайт відкривався.

## Що стереже від поломок

| коли | що | червоне означає |
|---|---|---|
| перед релізом | `tools/check-closures.py` | вкладена функція затінила зовнішнє ім'я |
| перед релізом | `py_compile` на Python 3.9 | публічний сервер не запуститься там, де його поставлять |
| перед релізом | `tools/smoke.py` на **фікстурі** | зламався код |
| щоночі, 07:15 | `tools/smoke.py --mode canary` на живому зрізі | змінилися дані, подивись |
| щохвилини | `tools/probe.py` зі шлюза | вузол лежить |
| щохвилини | `systemctl is-active nginx` у тій самій пробі | nginx не під systemd |

Фікстура — `tools/make-fixture.py`: тонкий зріз зрізу навколо семи статей, на
яких тримаються золоті числа. Дані в ній не міняються ніколи, тому червоне на
релізі не сплутати зі звичайною зміною закону.

У відкритому репозиторії лежать транспорт і перевірки, які працюють без
корпусу; саме ядро й фікстура — у закритому. Тому там `build-release.py`
пропускає дим і каже про це вголос: мовчазний пропуск нічим не відрізнявся б
від релізу без перевірок.
